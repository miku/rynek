# Feedback on initial scaffold

The basic abstractions in @rynek.go are very similar to the spotify/luigi code.
Plus: clear and simple interface. Con: May not be the most idiomatic Go going
forward.

Biggest issue is that in Python, the framework could blend in into the language
much more. The luigi Task class managed to expose class attributes (similar to
django model fields, or sqlalchemy columns, ...) to manage e.g. parameters. The
cli interface could be built up without lots of boilerplate.

The code in @example/example.go looks very verbose. Explicit is good, but we
need some kind of shortcuts, that nonetheless still look idiomatic. One of the
authors of luigi mentioned that basing all tasks on classes first (an not
functions) look a bit like a limitation. I wonder if we could explore this. Could a simple function be used as a building block?

Here are some inspiring ideas:

* the repo at @~/code/encoredev/encore is a project, that is written in Go, but
  uses ast parsing to build up a meta view of the infra artifacts; could we use
  something similar with tasks? e.g. let an ast parser discover tasks (following
  a set of patterns) and then add a persistance layer with the common "caching"
  patterns, e.g. file based state system that we already explored?
* our aim and first goal is to cover multi-step data processes with
  heterogeneous tools (e.g. using shell commands should not look to weird) on
  single machines; this limits our "data" to the TB range; we are not really
  interested in larger scale, but it should be possible to flip a filesystem
  target (files) to a S3 layer, basically extensing the range from TB to PB
* we do not exchange data in memory, because not all data produced and consumed
  will fit into memory; some systems like prefect or dagster seem to default to
  in memory passage of data; we explicitly want fast, but file based interaction
* the concept of incremental computing is interesting; "Incremental computing,
  also known as incremental computation, is a software feature which, whenever
  a piece of data changes, attempts to save time by only recomputing those
  outputs which depend on the changed data.[1][2][3] When incremental computing
  is successful, it can be significantly faster than computing new outputs
  naively. For example, a spreadsheet software package might use incremental
  computation in its recalculation features, to update only those cells
  containing formulas which depend (directly or indirectly) on the changed
  cells." -- this is an advanced topic, but if somehow the incremental portion
  could fall out of other design contraints and decision, it could be a plus on
  the efficiency side
* we are competing with people stitching together shell scripts; we cannot make
  this too complicated; we may need some lightweight notation on top, that
  would not feel much heavier than shell scripts
